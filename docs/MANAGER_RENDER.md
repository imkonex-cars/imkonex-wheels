# Серверный каталог и кабинет менеджера

Основная пошаговая инструкция: [UPGRADE_v0.5.0.txt](../UPGRADE_v0.5.0.txt).

## Архитектура

Один процесс FastAPI (`backend.portal:app`) обслуживает `dist/`, динамический публичный `data/catalog.js`, подбор `/api/fitment/…` и закрытые `/api/manager/…`. SQLite хранится по `MANAGER_DB_PATH` на постоянном диске. Веб-сервис читает публичную выгрузку из репозитория при старте. Успешный импорт в GitHub обновляет этот файл; автопубликация Render перезапускает сервис с новой выгрузкой. Сохранённые цены и заказы остаются на диске.

Достаточно одного экземпляра и одного worker. Для горизонтального масштабирования понадобятся общая SQL-база, общие лимиты и распределённая блокировка отправки. Текущую SQLite-конфигурацию не запускайте с несколькими независимыми дисками.

Dockerfile собирает frontend на Node 22 и запускает Python 3.12. `scripts/start-portal.py` берёт порт из `PORT`; по умолчанию 10000. Секреты не нужны во время сборки. Рекомендация для старта: 1 vCPU, 2 ГБ RAM и 1 ГБ постоянного диска. Это оценка для текущего каталога, не результат нагрузочного теста.

Render Static Site и Web Service имеют разные адреса. Только Web Service применяет правила цен из закрытой базы. На старом Static Site можно оставить витрину до проверки нового сервиса; после перехода направьте покупателей на новый адрес.

## Переменные

| Переменная | Значение |
|---|---|
| `MANAGER_LOGIN` | Логин кабинета, по умолчанию `manager` |
| `MANAGER_PASSWORD` | Отдельный пароль от 12 символов, без значения вход отключён |
| `MANAGER_DB_PATH` | `/var/data/manager.sqlite3` на постоянном диске |
| `FOURTOCHKI_LOGIN` / `FOURTOCHKI_PASSWORD` | Доступ к API, только Render Environment |
| `SUPPLIER_ORDERS_ENABLED` | `false` первоначально; `true` включает подтверждённую отправку |
| `PUBLIC_ORIGIN` | Для своего домена: точный адрес вида `https://wheels.example.ru`, без пути. Для адреса Render берётся `RENDER_EXTERNAL_URL` |
| `LOCAL_DEV` | Только локально `true` разрешает cookie без HTTPS; на публичном сервере не задавать |

Пароль менеджера и пароль API — разные значения. Секреты из GitHub Actions не доступны Render автоматически. Вход требует cookie; Safari/Chrome в обычном режиме поддерживаются. При `origin_rejected` сверьте домен и `PUBLIC_ORIGIN`. После смены домена войдите повторно на основном адресе.

## Цены

Фиксированная цена задаётся на артикул. Наценка считается от подтверждённой закупки каждого склада:

`продажа = округлить_вверх_до_10(закупка + max(закупка × процент / 100, минимум_руб))`

Режим «Розничная цена поставщика» возвращает цену из последней успешной публичной выгрузки. Рекомендуемая розница не является закупкой. Закупка никогда не записывается в JSON репозитория. В интерфейсе кабинета видно время чтения закупки; до первого чтения отображается прочерк.

Для артикулов с наценкой сервер обновляет закупку в фоне при старте и каждые 6 часов, пакетами до 50 артикулов. На цикл выделено не более 10 минут; при ошибке он прекращается. Цены, основанные на закупке старше 24 часов, не публикуются до обновления. Обновление страницы витрины получает новое правило в пределах 15 секунд; открытая вкладка сама цены не перерисовывает.

Остатки витрины берутся из публичной выгрузки. Перед созданием заказа остаток и закупка читаются заново. Показанная разница цены и закупки не учитывает доставку, налоги, комиссии и остальные расходы.

## Заказы

Вход защищён серверной сессией в HttpOnly/Secure/SameSite cookie; изменения требуют проверенного Origin и CSRF-токена. Браузер передаёт только артикул, склад, количество и пожелание test; цены вычисляются сервером. Клиентские имя/телефон сохраняются только в закрытой базе и автоматически поставщику не передаются.

Предпросмотр живёт 120 секунд. Перед `CreateOrder` сервер повторно проверяет закупку/остатки и атомарно помечает заказ как отправляемый. В SOAP передаются конкретные склады и количества, `skip_error_61=false`, `useBonus=false`, `priceIn` — розничная цена клиента согласно документации поставщика, `base_order.orderNumber` и комментарий — уникальный номер IMX.

`is_test=true` создаёт запись «я формирую» у поставщика. `false` передаёт боевой заказ для резервирования. Доставку, оплату, бонусы, отмену заказа и изменение его состава через этот кабинет версия 0.5.0 не оформляет.

После таймаута нельзя определить, выполнена ли операция. Такой заказ блокируется от повторной отправки. Менеджер проверяет внешний кабинет и связывает найденный номер; связь сама новый заказ не создаёт. Если запись не найдена, сначала получите подтверждение поставщика об отсутствии заказа и только затем формируйте новый.

Информация об исполнении запрашивается через `GetOrderInfo2`: статус, оплата, отгрузка, пункт выдачи, адрес и интервал доставки. Обновление — по кнопке и раз в минуту при открытой карточке. Сохраняются увиденные изменения статуса. Заказы, созданные вне нашего кабинета, автоматически в список не импортируются.

## Категории и подбор

Точное сопоставление типов: `car`, `vned` → легковые/SUV; `cartruck`, `truck` → грузовые/коммерческие; `moto`, `quadbike` → мото/квадроциклы; `specteh`, `selhoz`, `loader` → спецтехника; неизвестный тип → только «Все шины». Диски имеют отдельный раздел; запрос камер использует subtype 0. Ободные ленты и уплотнительные кольца не включаются в камеры.

Расширение включено в `config/sync.json`: `extended_categories=true`, `include_tubes=true`. Поддержка новых категорий требует следующего успешного импорта. При недоступности метода камер проверьте ошибку/схему и разрешения аккаунта. Для продолжения импорта шин и дисков можно временно установить `include_tubes=false`; типы шин сохранятся. Если камеры уже публиковались, массовое уменьшение их количества остановит импорт — сначала проверьте причину, затем используйте осознанное `allow_large_drop`.

Подбор использует GetMarkaAvto, GetModelAvto, GetYearAvto, GetModificationAvto и GetGoodsByCar. Запрашивается только podbor_type=1, типы tire/disk; ответ пересекается с доступными артикулами нашей выгрузки. Перед покупкой проверяются индексы нагрузки/скорости, штатные параметры и конкретная комплектация. Для разношироких осей не считайте весь найденный список одним одинаковым комплектом.

## Резервные копии

Постоянный диск сохраняет базу между развёртываниями. Для независимой копии откройте Shell сервиса и выполните, указав новую дату/имя:

```sh
python scripts/backup-manager.py /var/data/backups/manager-20260922.sqlite3
```

Скрипт использует SQLite backup API и включает подтверждённые транзакции WAL. Скачайте копию в закрытое хранилище. Не загружайте её в GitHub или общедоступную папку. Копия на том же диске не защищает от удаления самого диска. Резервное копирование по расписанию этой сборкой не настроено.

Восстановление делайте при остановленном приложении, из проверенной копии, с сохранением текущей базы перед заменой. Не копируйте рабочий sqlite-файл без WAL обычной командой во время записи.

## Локальный запуск и проверка

Для Docker Compose скопируйте `.env.example` в `.env`, задайте свои значения, `PUBLIC_ORIGIN=http://localhost:8080` и `LOCAL_DEV=true`, затем `docker compose up --build -d`. Адрес `http://localhost:8080/`. База хранится в отдельном томе. `docker compose down` сохраняет том; не используйте `down -v` при ценных заказах.

Для публичного VPS задайте `APP_DOMAIN`, HTTPS `PUBLIC_ORIGIN`, удалите `LOCAL_DEV` и запустите профиль `public` с Caddy. Основной рассматриваемый путь размещения — Render, отдельный автомобильный каталог не затрагивается.

Автоматические тесты не используют реальные секреты и не создают заказы у поставщика. Docker daemon в среде подготовки недоступен: проверены исходная сборка, Python-сервер и контракты; первую сборку контейнера выполняет Render. Настоящий подбор/новые категории/новые операции заказов требуют проверки с вашим аккаунтом после установки.
