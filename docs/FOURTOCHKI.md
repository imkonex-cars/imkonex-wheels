# Подключение 4tochki: готовая основа и оставшаяся работа

Справка поставщика: [b2b.4tochki.ru](https://b2b.4tochki.ru/Help/Page?url=index.html). WSDL: [ClientService.svc](https://api-b2b.4tochki.ru/WCF/ClientService.svc?wsdl).

В изученных материалах есть операции поиска шин/дисков, информации о товарах, ценах, остатках, складах и подбора по автомобилю. Наличие названия метода не подтверждает доступ к данным в конкретной учётной записи, полноту фото и применимости, разрешённую частоту запросов или условия использования контента.

В этом выпуске нет обещания работающей синхронизации: подготовлены безопасный SOAP-клиент, просмотр схем, запросы только на чтение и транзакционный импорт уже нормализованного JSON. Реальный ответ поставщика в бизнес-модель ещё не преобразуется.

## Диагностика без пароля

```bash
.venv/bin/python -m backend.supplier inspect
```

Команда загружает WSDL и связанные схемы, выводит сигнатуры разрешённых методов. HTTP-ссылки на импортированные схемы того же хоста переводятся на HTTPS. Внешние хосты и перенаправления блокируются. XML DTD и внешние сущности запрещены. Сетевые операции ограничены таймаутами.

Изученные имена методов включены в список разрешённых: `GetFindTyre`, `GetFindDisk`, `GetGoodsInfo`, `GetGoodsPriceRestByCode`, `GetWarehouses`, `GetDeliveryPeriod`, `GetGoodsByCar`, `GetMarkaAvto`, `GetModelAvto`, `GetYearAvto`, `GetModificationAvto`, `GetPrice`, `GetRest`. Актуальная WSDL может отличаться; команда покажет доступные совпадения.

## Проверка конкретного запроса

Храните `FOURTOCHKI_LOGIN` и `FOURTOCHKI_PASSWORD` в окружении сервера. `.env` читается Docker Compose; при запуске Python напрямую его нужно загрузить средствами своей среды, приложение автоматически его не читает.

После изучения **реальной сигнатуры** создайте приватный `runtime/probe-arguments.json`. Ключи, вложенность и значения фильтров должны точно соответствовать схеме. На место учётных данных можно поставить строки `$LOGIN` и `$PASSWORD`: клиент подставит их из переменных окружения. Универсальный пример имени поля логина здесь намеренно не приводится — без схемы он был бы предположением.

```bash
.venv/bin/python -m backend.supplier probe GetFindTyre runtime/probe-arguments.json
```

Команда выводит только статус транспорта и тип результата. HTTP/SOAP-ответ без исключения не считается подтверждением делового успеха: поставщик может вернуть код ошибки внутри тела. Для реального обмена требуется обработка этого кода.

Методы изменения, в том числе `CreateOrder`, не входят в список разрешённых. Ни витрина, ни API, ни worker не могут разместить заказ через этот адаптер.

## Что нужно реализовать на действующих данных

1. Проверить схему авторизации и выполнить несколько чтений конкретных артикулов, складов и применимости. Согласовать с поставщиком ограничения запросов и обновления.
2. Разделить сущности: модель товара, размерный артикул, складское предложение и применимость. Сохранить исходные идентификаторы и время получения данных.
3. Нормализовать параметры шин и дисков, единицы измерения, индексы, цвета, URL фото, сроки и остатки. Проверять ошибки поставщика и неполные выгрузки; не затирать рабочий снимок невалидной или случайно пустой выгрузкой.
4. Держать закупочную цену в закрытом серверном хранилище. Рассчитывать розничную цену на сервере по правилам наценок. Публичный `Catalog` принимает только розничные предложения и отвергает лишние поля.
5. Сделать стабильное сопоставление ответа с `backend.models.Catalog`, дедупликацию, дозапросы страниц, backoff и журнал ошибок без паролей. В этой версии такого преобразователя нет.
6. Передать готовый JSON worker или команде `backend.repository import`. Проверить атомарное обновление на PostgreSQL и сверку остатков перед подтверждением заявки.
7. Подключить интерфейс к API, а после подтверждения применимости и работы менеджеров отдельно реализовать жизненный цикл настоящего заказа с идемпотентностью и сверкой статуса.

Имеющиеся в прошлой переписке пароли в репозиторий не переносились. В этой сборке авторизованные запросы поставщику не выполнялись.
