# Личный кабинет и вход по телефону — 0.9.0

Подготовлена серверная регистрация/авторизация по одноразовому коду и страница `/account/`.
При первом успешном подтверждении создаётся учётная запись, при следующих — открывается существующая.
Допустим российский мобильный номер: `+7 9XX ...`, `8 9XX ...` или десять цифр начиная с 9. Стационарные и международные номера не поддерживаются этим адаптером.

## Что уже делает модуль

- Код из 6 случайных цифр (`secrets`), действует 5 минут; не возвращается в JSON, не пишется в логи или БД открытым текстом.
- HMAC-SHA256 с отдельным серверным ключом; в БД хранится производная кода с уникальным идентификатором запроса.
- Код привязан к браузерной сессии входа, одноразовый. После пяти неверных попыток блокируется; повторная отправка отменяет прежний код.
- Атомарное погашение кода и создание сессии в одной SQLite-транзакции, в том числе при одновременной проверке несколькими запросами.
- Сессия на 30 дней; токен только в cookie `HttpOnly; Secure; SameSite=Strict`, путь `/api`. В БД — HMAC токена.
- Origin + CSRF для отправки/проверки кода и всех авторизованных изменений. Авторизация менеджера остаётся отдельной.
- Лимиты хранятся в БД, действуют после перезапуска: 1 SMS/минуту, 5/час и 10/сутки на номер; 20/час на IP; общий предел 100/час и 500/сутки. Проверка кода — 60/час на IP плюс 5 на код. Получение браузерного nonce — 60/час на IP.
- Профиль: имя и подтверждённый телефон. Телефон не меняется простым редактированием поля.
- Заказы: только заявки, явно привязанные к `customerAccountId` во время авторизованного оформления. Исторические заявки **не** привязываются по совпадению телефона. Закупочные цены, приватные ссылки/токены и данные поставщика не возвращаются.
- Без настроенного SMS-провайдера вход недоступен, API отправки возвращает `503 sms_not_configured`. Нет демонстрационного кода или обходного аккаунта. Клиент видит возможность обратиться к менеджеру.

## Включение SMS.ru

В закрытом окружении сервера:

```dotenv
CUSTOMER_AUTH_SECRET=<случайный_серверный_ключ_не_короче_32_символов>
SMS_PROVIDER=smsru
SMS_RU_API_ID=<идентификатор_из_личного_кабинета_SMS.ru>
SMS_RU_SENDER=<согласованное_имя_отправителя_если_нужно>
PUBLIC_ORIGIN=https://wheels.imkonex.com
```

`backend/sms_ru.py` реализует отдельный адаптер официального метода `sms/send`. Требуется действующий аккаунт/баланс SMS.ru и согласованные условия отправки. Само наличие кода не подтверждает прохождение SMS конкретному абоненту. Живых отправок при разработке не выполнялось.

Не устанавливать `LOCAL_DEV=true` на публичном сервере. Перезапуск с другим `CUSTOMER_AUTH_SECRET` инвалидирует действующие сессии и коды.

## Альтернатива: ваш HTTPS SMS-шлюз

Это **наш явно определённый контракт промежуточного шлюза**, а не выдуманная совместимость с API какого-либо оператора. Для подключения другого SMS-сервиса необходимо реализовать его адаптер `SmsSender` по официальной документации или отдельный шлюз с таким контрактом.

```dotenv
CUSTOMER_AUTH_SECRET=<случайный_серверный_ключ>
SMS_PROVIDER=custom
CUSTOMER_SMS_BRIDGE_URL=https://sms.example.com/otp
CUSTOMER_SMS_BRIDGE_TOKEN=<секрет_для_вашего_шлюза>
```

Провайдер `custom` отправляет один HTTPS POST:

```http
Authorization: Bearer <CUSTOMER_SMS_BRIDGE_TOKEN>
Idempotency-Key: <идентификатор_попытки>
Content-Type: application/json
```

```json
{"phone":"+79991234567","message":"Шины и диски: код входа ..."}
```

Принятие: HTTP 200 или 202 и JSON `{"accepted":true}`. Все остальные ответы/ошибки означают неуспешную либо неподтверждённую отправку, код становится недействительным. Автоматических повторов, перенаправлений, отключения TLS-проверки нет. Сам шлюз должен дедуплицировать `Idempotency-Key` и не сохранять текст кода в общедоступных журналах.

## Подключение в приложении

До `app.mount('/', ...)`:

```python
from .customer_auth import register_customer_routes
customer_auth = register_customer_routes(
    app, store, origin=origin, secure_cookie=secure_cookie,
)
```

`origin(request)` — существующая проверка точного `PUBLIC_ORIGIN`. `store.path` — приватная SQLite-база на постоянном диске. Модуль создаёт только собственные таблицы, не переопределяя менеджерские сессии.

API:

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/customer/auth/bootstrap` | `available`, а при готовности — CSRF и временная HttpOnly cookie |
| POST | `/api/customer/auth/request` | `{phone, consent:true, consentVersion:"2026-09-24"}` → `challengeId`, `expiresIn`, `retryAfter` |
| POST | `/api/customer/auth/verify` | `{challengeId,code}` → `{customer:{id,phone,name},csrf}` и сессионная cookie |
| GET | `/api/customer/me` или `/api/customer/session` | `{customer:{id,phone,name},csrf}` либо 401 |
| PATCH | `/api/customer/me` | `{name}` → `{saved:true}` |
| GET | `/api/customer/orders` | `{orders:[...]}` — только принадлежащие аккаунту |
| POST | `/api/customer/auth/logout` | удаление сессии и cookie |

Пишущие запросы должны отправлять `Origin` и `X-CSRF-Token` из соответствующего этапа. Токен CSRF после входа отличается от CSRF формы входа. Не класть сессионные токены в localStorage или URL.

Другие модули используют:

```python
customer = app.state.customer_auth.current(request, required=False)
```

Для действующей сессии возвращаются `id, phone, name, csrf`; на изменяющем запросе проверяются Origin/CSRF. Без сессии — `None`, если `required=True` — HTTP 401. Привязка новой заявки должна проверять равенство нормализованного телефона заявки подтверждённому телефону. Нельзя принимать `customerAccountId` от браузера.

Все пути `/api/customer` и `/account` должны получить `Cache-Control: no-store`, включая ответы с ошибками. Статические файлы автоматически попадают в `dist/account` при стандартной сборке проекта.

## Эксплуатационные ограничения

- В этой реализации имя/телефон хранятся в существующей приватной БД, защищённой правами файла и закрытым томом, **без шифрования отдельных полей**. Нужно обеспечить приватные бэкапы и установленный срок хранения. Это не заявление о полной готовности всех требований к обработке персональных данных.
- IP берётся из `request.client.host`; произвольному `X-Forwarded-For` модуль не доверяет. Настроить доверенный адрес reverse proxy в Uvicorn. Нельзя разрешать прокси-заголовки от всего интернета. Если все клиенты видны под IP прокси, лимит будет общим для них.
- До рекламы и большой нагрузки подключить CAPTCHA/антибот перед платной отправкой, настроить бюджет и оповещения в кабинете SMS-провайдера. Общий предел в модуле — технический лимит, а не финансовый мониторинг.
- Смена SIM/передача номера другому владельцу требует отдельной политики восстановления и защиты аккаунта. Исторические гостевые заказы не подхватываются автоматически.
- Оплата, сохранённые карты, бонусы и реальная выдача по QR этой страницей не имитируются. Список заказов отображает действительные статусы существующего процесса заявок.

## Проверка

```bash
python -m pytest -q tests/test_customer_auth.py
```

Проверяются конкурентное погашение, просрочка, пять попыток, сохранение ограничений после перезапуска, сбой SMS, Origin/CSRF, cookie, выход, смена ключа, собственные/чужие заказы и отсутствие выдачи приватных полей. Отправщик SMS в тестах подставной; он находится только в тестовом коде.
