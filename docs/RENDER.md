# Публикация демонстрации на Render

## Основной вариант: статическая витрина

Это рекомендуемый первый этап. Браузер получает готовые HTML, CSS, JavaScript и изображения. Бесплатный спящий API не нужен для просмотра каталога.

Создайте приватный репозиторий GitHub и поместите в него исходники. Если работаете через Git:

```bash
git init
git add .
git commit -m "Initial IMKONEX wheels demo"
git branch -M main
git remote add origin https://github.com/YOUR_ACCOUNT/imkonex-wheels.git
git push -u origin main
```

Замените `YOUR_ACCOUNT` на своё имя пользователя. GitHub авторизуйте обычным способом; токен не вставляйте в URL или исходники. Архив содержит папку `imkonex-wheels` — корнем репозитория должно стать её содержимое, а не дополнительный уровень вложенности.

В Render подключите GitHub и разрешите доступ только к этому репозиторию. Создайте **New → Static Site**:

| Настройка | Значение |
|---|---|
| Branch | `main` |
| Root Directory | пусто |
| Build Command | `npm run build` |
| Publish Directory | `dist` |
| Environment | `NODE_VERSION=22` |

Либо создайте Blueprint из корневого `render.yaml`: в нём заданы те же параметры и защитные HTTP-заголовки. Путь фильтра хранится после `#`, поэтому catch-all rewrite не требуется. Обновление ветки запускает новую сборку.

Для сборки витрины `npm install` не нужен: зависимостей времени выполнения нет. `npm ci` используется в CI для установки инструмента DOM-тестов.

Оставьте `PUBLIC_API_BASE` пустым для полностью автономной демонстрации. Не создавайте PostgreSQL и фоновые сервисы на этом этапе. Сайт остаётся публично доступным по выданному Render адресу, даже если GitHub-репозиторий приватный.

## Необязательный демонстрационный API

Можно создать второй Blueprint, указав путь `render-api.yaml`, либо Python Web Service с параметрами из файла. Выберите именно **Free**. Не включайте платную базу или диск.

Укажите `ALLOWED_ORIGINS` равным точному HTTPS-адресу витрины, без завершающего `/`. После публикации API проверьте `/health` и `/docs`. Затем на статическом сайте задайте `PUBLIC_API_BASE=https://YOUR_API.onrender.com` и запустите повторную сборку. Это включает кнопку проверки API в демо-кабинете; сами товары в интерфейсе остаются статическими.

У бесплатного web service 512 МБ памяти и 0.1 CPU по текущей документации. Он засыпает после 15 минут отсутствия входящего трафика; пробуждение может занимать около минуты. Проверка из кабинета ждёт 8 секунд: при холодном старте откройте `/health`, дождитесь ответа и повторите. Файловая система непостоянная, бесплатный PostgreSQL ограничен 1 ГБ и истекает через 30 дней. Поэтому сервер этой конфигурации не сохраняет реальные заявки и ничего не синхронизирует по расписанию. [Бесплатные сервисы Render](https://render.com/docs/free), [спецификация ресурсов](https://render.com/docs/blueprint-spec).

## Проверка после публикации

Откройте каталог на компьютере и телефоне. Проверьте фильтр размера, переход по скопированной ссылке, сравнение, корзину и карточку товара. Убедитесь, что загружены фотографии и предупреждение о тестовых данных видно. Проверьте отсутствие ошибок JavaScript, горизонтального переполнения и недоступных кнопок при клавиатурной навигации.

Для собственного домена API обновите также `connect-src` в Content-Security-Policy файла `render.yaml`: по умолчанию разрешены тот же домен и адреса `*.onrender.com`.

Настройки сверены с [документацией статических сайтов](https://render.com/docs/static-sites) и [Blueprint YAML](https://render.com/docs/blueprint-spec) 14.09.2026. Сам деплой и проверка аккаунтных квот не выполнялись: GitHub и Render ещё не подключены к этой рабочей сессии.
