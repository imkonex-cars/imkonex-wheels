# Запуск на отдельном VPS

Стартовый ориентир: 4 vCPU, 8 ГБ RAM, 120–160 ГБ NVMe. В этой версии это среда пилота и интеграции. Для большой выгрузки нужно перенести фильтрацию в SQL, добавить кэш снимка и проверить нагрузку: текущий API читает полный снимок на запрос.

## Локальный Docker / закрытый первый запуск

Установите актуальный Docker Engine и Compose по документации вашей ОС. Скопируйте проект и создайте `.env` из `.env.example`.

Сгенерируйте отдельный случайный пароль PostgreSQL. Один и тот же пароль укажите в `POSTGRES_PASSWORD` и `DATABASE_URL`; удобнее использовать 64 шестнадцатеричных символа, чтобы не требовалось URL-кодирование. Не оставляйте пример из файла.

```bash
cp .env.example .env
# Отредактируйте .env перед запуском.
docker compose up -d --build
```

Витрина и API доступны на `http://127.0.0.1:8080`. Порт приложения привязан к loopback; PostgreSQL наружу не опубликован. По умолчанию используется `DATA_MODE=demo`, поэтому миграции для этого первого просмотра не нужны.

На удалённом VPS доступ можно проверить через SSH-туннель, не открывая приложение миру. Не меняйте привязку PostgreSQL на публичную.

## Проверить постоянное хранение каталога

```bash
docker compose exec app python -m backend.repository migrate
docker compose exec app python -m backend.repository import data/demo-catalog.json
```

Затем измените в `.env` `DATA_MODE=postgres` и пересоздайте приложение:

```bash
docker compose up -d app
```

`/health` по-прежнему показывает `mode: demo`, потому что импортированы тестовые товары. Изменение хранилища не превращает данные в реальные. Витрина остаётся статической; её связь с живым API — следующий этап.

Импорт заменяет весь публикуемый каталог в одной транзакции. Файл сначала проходит строгую проверку. Ошибка записи откатывает транзакцию, сохраняя предыдущий снимок. Предусмотрены индексы и история успешных импортов.

## Домен и HTTPS

Направьте DNS A/AAAA своего поддомена на VPS. Откройте входящие 80/443, оставив доступ к SSH в рамках действующей политики сервера. В `.env` задайте `APP_DOMAIN=tires.YOUR_DOMAIN` и `ALLOWED_ORIGINS=https://tires.YOUR_DOMAIN`. Публичный профиль включает Caddy:

```bash
docker compose --profile public up -d
```

Caddy завершает HTTPS и проксирует приложение. До подключения настоящих данных сохраняются `noindex` и демо-маркировки.

## Импорт по расписанию

Фоновый сервис читает **готовый нормализованный JSON**, а не сырой ответ 4tochki. Сначала нужен преобразователь реального ответа поставщика.

Создайте `runtime/feeds/`, поместите туда `catalog.json`, проверьте соответствие `backend.models.Catalog`. Пользователь контейнера UID 10001 должен иметь доступ на чтение. Публикуйте новый файл атомарным переименованием, чтобы worker не увидел недописанный JSON.

```bash
docker compose --profile sync up -d worker
```

Worker проверяет файл раз в 900 секунд по умолчанию и импортирует только изменившееся содержимое. Заказы у поставщика он не создаёт.

## Резервные копии

```bash
sh scripts/backup.sh
```

Скрипт создаёт дамп PostgreSQL в `backups/`. Выгружайте копии на отдельное хранилище; локальная папка на том же диске не защищает от потери VPS. Расписание и удалённая выгрузка в этом пакете автоматически не включены.

Проверку восстановления выполняйте в **отдельной тестовой базе**, не поверх рабочей. Пример:

```bash
docker compose exec db createdb -U imkonex restore_check
docker compose exec -T db pg_restore -U imkonex -d restore_check < backups/YOUR_BACKUP.dump
```

Не выполняйте `docker compose down -v` на рабочем сервере: это удаляет том PostgreSQL. Обновление исходников делайте с новой сборкой контейнера и предварительным резервным копированием.

Docker и PostgreSQL в текущей среде сборки отсутствовали; контейнерный запуск, миграции на реальной БД, HTTPS и восстановление дампа нужно проверить на VPS перед эксплуатацией.
