# IMKONEX CARS · каталог шин и дисков 0.4.0

Полная рабочая область для существующего GitHub-репозитория и Render Static Site.
Обновление добавляет массовую выгрузку доступных шин и дисков из API «4точки» и запуск через GitHub Actions. Рабочая проверочная выборка из шести товаров с локальными фотографиями входит в архив и отображается до первой успешной выгрузки. Цены и остатки этой исходной выборки относятся к 17.09.2026; установка новой версии не делает их свежими.

Репозиторий: https://github.com/imkonex-cars/imkonex-wheels
Сайт: https://imkonex-wheels-demo.onrender.com/

Начните с START_HERE_PC1.txt. Подробная инструкция: docs/SYNC_SETUP.md.

## Что делает обновление

- Обходит страницы GetFindTyre и GetFindDisk, определяет начало нумерации и контролирует количество страниц. GetGoodsInfo запрашивается пакетами с точным сопоставлением артикулов. Используются поля, подтверждённые отчётом пользователя от 17.09.2026; перед отправкой запросы проверяются по загруженной WSDL.
- Использует только price_rozn — розничную цену поставщика в подтверждённых RUB. Закупочная price не переносится в публичный снимок, файл отчёта или журнал. Наценка IMKONEX не применяется.
- Сохраняет отдельные предложения каждого склада. Комплект из четырёх штук должен быть доступен на одном складе. Срок доставки остаётся «уточняется».
- Сохраняет исходные артикулы. Неизвестный код сезона отображается как «Сезон уточняется». Тип диска и RunFlat не угадываются.
- Публикует товары с розничной ценой, наличием и поддержанными характеристиками. Неподдержанные параметры и отсутствие доступного предложения учитываются в результате выгрузки; это не обещание отобразить каждую позицию поставщика.
- Сохраняет ранее скачанные фотографии. Новые оригиналы скачиваются по публичным адресам поставщика; одинаковые ссылки используют один файл. Лимиты кеша и загрузки задаются в config/sync.json. Остальные фото используют публичные HTTPS-ссылки, при ошибке остаётся заглушка.
- Заменяет снимок после завершения всей выгрузки и проверки публичного формата. Сетевой сбой, ошибка авторизации, повтор страниц, изменение количества страниц, отсутствующие характеристики или неверная валюта сохраняют прежние данные. Снижение числа публикуемых товаров более чем на 50% в любой категории требует проверки результата и ручного запуска с allow_large_drop.
- Отображает время последней успешной выгрузки и предупреждение, когда данные старше суток. Интерфейс выводит 12 карточек на страницу и ограниченное число кнопок навигации.

## Размещение и запуск

| Настройка Render | Значение |
|---|---|
| Тип | Static Site |
| Root Directory | пусто |
| Build Command | node BUILD_RENDER.mjs |
| Publish Directory | dist |
| NODE_VERSION | 22 |
| Auto-Deploy | On Commit, если не используете Deploy Hook |

В GitHub Secrets добавьте FOURTOCHKI_LOGIN и FOURTOCHKI_PASSWORD. В Actions запустите Sync 4tochki catalog. Workflow проверяет код, читает API, строит сайт и записывает проверенный публичный снимок с фотографиями в ветку по умолчанию. Render публикует этот коммит. Пароль поставщика нужен только шагу выгрузки в Actions; в переменные статической сборки Render его добавлять не нужно.

Для явного запуска Render предусмотрен необязательный секрет RENDER_DEPLOY_HOOK_URL. В этом варианте переключите Auto-Deploy Render в Off, чтобы не запускать две сборки на каждый коммит. Инструкция обоих вариантов есть в docs/SYNC_SETUP.md.

После первого успешного запуска включите расписание переменной GitHub Actions CATALOG_AUTO_SYNC=true. Начальная частота — два раза в сутки, в 02:23 и 14:23 UTC (07:23 и 19:23 Челябинск). Запуски GitHub могут задерживаться. Частоту следует увеличивать после проверки длительности, лимитов площадок и условий API поставщика.

## Состав проекта

Корень содержит BUILD_RENDER.mjs, package.json, package-lock.json, requirements*.txt, render.yaml, README.md, START_HERE_PC1.txt и дополнительные файлы разработки. Папки: backend, config, data, deploy, docs, frontend, scripts, tests, .github. Полный перечень находится в FILES_MANIFEST.txt. SYNC_CATALOG_WORKFLOW.txt — точная копия нового workflow для ручного создания файла .github/workflows/sync-catalog.yml через интерфейс GitHub.

Действующий публичный снимок: data/supplier-snapshot.json. После синхронизации это schemaVersion=3. Поле frontend/data/catalog.js генерируется сборкой и вручную не редактируется. Проверки используют постоянную публичную фикстуру tests/fixtures/public-sample.json, поэтому не требуют прежних цен и ровно шести товаров в рабочем каталоге.

Backend API, Docker и PostgreSQL сохранены как исходники прежнего этапа; данная публикация на Render использует статическую сборку и GitHub Actions. Импорт в PostgreSQL, подбор по автомобилю, приём заявок менеджером, заказы поставщику и оплата в этой версии не подключены.

## Проверки и локальные команды

```bash
npm ci
npm test
npm run build
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -p test_catalog_sync.py -v
python -m pytest -q tests/test_api.py tests/test_catalog_check.py tests/test_export_snapshot.py tests/test_supplier_check.py tests/test_supplier_schema_imports.py
```

Для локальной синхронизации используйте Python 3.12 и Node.js 22+, установите requirements-sync.txt и задайте переменные FOURTOCHKI_LOGIN / FOURTOCHKI_PASSWORD средствами своей среды, затем выполните python -m backend.catalog_sync. Файл .env автоматически не читается. --dry-run проверяет кандидат без изменения текущего снимка. Диагностический runtime/sync-summary.json содержит только служебные счётчики и фиксированный код ошибки; он исключён из GitHub.

Статическая сборка не вызывает API и не требует пароля. Если выгрузка прерывается из-за лимита, она не публикует усечённый каталог. Защиты пилота: максимум 50 000 просмотренных артикулов, 32 МБ публичного JSON, 35 минут обмена API по умолчанию, 100 новых фотографий за запуск и кеш 100 МБ. При превышении нужно измерить объём и выбрать следующие настройки либо серверную архитектуру.

Проверки версии и границы подтверждения: docs/VALIDATION_0_4.md.
